## 4. 合成入力の生成規則

同じ指定(ステート数・国家数・1ステートあたりのプロヴィンス数・seed)から同じ入力ができる。乱数は SplitMix64 を `seed`・用途・ID から導出する(生成順・`HashMap` の順序に依存しない。規模を1増やしても先頭のステートは同じ配置になることをテストで確認)。

- **地理**: 実地図(`assets/data/hex_atlas_map.json`)の陸セル(34,503個)を `(r, q)` 順に並べ、seedで決めた位置から巡って、幅優先で6セルずつのステートに区切る(連続した陸で、ステートは連結)。6セルに満たない断片は捨てる(1000ステートで12個)。プロヴィンスIDは既存の全世界の初回採番(`generate_initial_province_table`)と同じ値。ステートIDは 1..=N(新しい `MapStateId` で、旧 `StateId` との数値変換は行わない)。
- **世界**: 既存の `ProvinceTableFile`(`coverage: Partial`)と `StateLayoutFile` を `WorldModel::build` と Authoring検証(地図との整合)に通す。`load_world_preview` と同じ検証。
- **人口・生活**: 人口150,000〜900,000、労働力比率0.40〜0.60、生活水準40〜70(整数。曖昧な 0〜1 の範囲を避ける)、不満度5〜25、基礎物流150〜300。
- **施設(初期)**: Farm 1〜5、Railway 1、Factory 0〜2、Mine 0〜2(鉱床のあるステートだけ)。1000ステートの合計: Farm 2975 / Railway 1000 / Factory 1034 / Mine 821。MilitaryFactory等は置かない。
- **資源**: プロヴィンスごとに25%の確率で鉱床1つ(Iron/Coal 半々、産出10〜40、発見済み80%、開発度1〜2)。全プロヴィンスを設定済み(資源なしの明示を含む)。1000ステートでは1497プロヴィンス(Iron 704 / Coal 793)。ステート単位の鉱床入力は空(プロヴィンス別が正本)。
- **国家**: ステートID順に連続した塊で割り当て、各国家に最低 ⌊N/C⌋ 個(1000/3 → 333〜334、1000/100 → 10)。国家1は手動、他はAI。国庫 3000+1500×担当ステート数、税率0.15、備蓄(Iron/Coal/Food/Wood)1000+300×担当ステート数。
- **建設・経済AI**: AI国家は月次の周期で税率調整と建設判断を行う(既存ロジック)。手動国家1は台本で、0・45・170・200・300日経過後(次の日の処理の前)に最大5ステートへ Farm/Factory/Mine/Railway を循環して発注する(連続実行にも復元後の継続にも同じ日付・順序で適用)。170日の発注により、分割日(180)に建設中の注文が残る。
- **隣接・施設キュー・位置施設**: 隣接は地図上の連結のみ(補給等には使われない)。位置施設(`LocationFacilityRegistry`)は経済に効果を持たないので載せていない。軍事状況の入力は与えない。

## 8. 正しさの判定

各ケースで以下をすべて確認し、成功の条件にしている(満たさなければ「正しさの失敗」)。

- **指定どおりの数**: 世界・経済のステート数、国家数、各国家が担当ステートを持つこと、担当の合計がステート数と一致すること、全ステートに人口と施設があること。
- **既存の検証を通る**: 世界(`WorldModel::build`+Authoring検証)、経済(共有の組み立て=シナリオ・資源・所属の検証)。検証を緩めていない(国家に属さないステートや地図に無い座標が拒否されることをテストで確認)。
- **決定性**: 同一条件の連続3回が、各回で指定日数(360)を処理して同じ日付で終わり、終了状態が完全比較(`==`)で一致し、件数(完成・AI注文・税率変更・評価・月次日数等)も一致。保存を挟む参照実行の終了状態も連続実行と一致。さらに、**別プロセスでの2回の測定**で、入力ダイジェストと終了状態ダイジェストが全ケースで一致した(例: 1000/3 の入力 `5ce51bdc6629cc4e`、終了状態 `ab5b73723aa4e005`)。
- **保存・再開の継続一致**: 180日処理して共有APIで一時ディレクトリへ保存 → 新しく組み立てたセッションへ復元 → 復元直後の状態が保存時の状態と完全一致 → 後半180日を、各日について(a)状態全体(保存対象のスナップショットのRON表現)のBLAKE3ダイジェスト、(b)その日の出来事(完成・AI注文・税率変更・評価・月次実行)を、連続実行側と比較(不一致0日)→ 最終状態の完全比較。並べ替え・丸め・許容誤差は使っていない。経済状態、国庫、施設、キュー、注文識別子、AI履歴を含む既存の動的状態が対象。
- **空・無変化を根拠にしない**: 比較日数が0、後半で状態が一度も変わらない(異なるダイジェスト<2)、後半に月次処理がない、保存時点で建設中の注文がない、建設活動が全くない、のいずれかなら成功にしない(テストで確認)。
- **結果の区別**: 成功 / 正しさの失敗 / 時間超過(未完了) / 実行不能を区別し、時間超過を不一致や完了済みの測定として扱わない(テストで確認)。
- **保存先**: 測定用の保存はOSの一時ディレクトリだけ。`saves` を含む場所は拒否。終了時に自分の1ファイルを消す。テストで `saves/map_economy/` の一覧が前後で不変であることを確認した。

月境界の保存再開(保存日の翌日が月替わり)と月の途中の保存再開は、どちらも小ケースのテストで一致を確認した(1000ステート規模の本番測定の保存日 1800/06/30 も、翌日が月替わり)。

## 9. 測定の限界(必ず併記)

- 合成モデルの結果であり、**正式な全世界のステート数・人口・資源・施設・国家配置・ゲームバランスを代表しない**。既存の検証シナリオ(m4d/m4e)と同一条件でもない。
- 1ステート6プロヴィンスで、実地図の陸セル全体(34,503)の約17%(6000セル)しか使っていない。プロヴィンス数が数万の実規模は未測定。実データのステート数がいくつになるかは決まっておらず、**1000ステートを超える規模は未測定**。
- 経済AIの活動は控えめ(国家3・1000ステートで360日のAI注文16、評価25)。建設キューが長く伸びる状況の負荷は測っていない。軍事状況・位置施設の効果・補給・移動・戦闘は含まない(未実装または対象外)。
- 時間はこのPC・この時点の1回ずつ(2回分)の値で、ハードウェア依存。標準偏差等は取っていない。小さいケースの値(0.3ms等)は計時分解能やキャッシュの影響が大きい。
- ピークメモリは未取得。OOMや強制終了は起きなかったが、メモリに余裕があったことの証明ではない。
- 各ケースの時間上限(120秒)は運用上の安全装置であり、性能の合否基準ではない。

## 10. 性能上の観察(根拠と改善候補。今回は最適化しない)

- **日次進行は小さい**: 1000ステートでも1日平均 0.08ms(月次処理日 約1.8ms)。ステート数に対しておおむね線形(300→1000で約3.5倍 ≒ ステート数比)。
- **保存・復元の時間がステート数に対して線形を超えて増える**(300ステート: 保存0.26s/復元0.25〜0.35s → 1000ステート: 保存2.4〜2.5s/復元4.4〜4.5s。ステート比3.3倍に対して約9〜18倍)。ファイルサイズは線形(243KB→766KB)。日次進行より桁違いに大きい。1000ステート・100国家では保存8.8s/復元10.6s。
- **原因は未特定**(根拠が無いので断定しない)。保存・復元の内側(静的入力の識別情報の計算、スナップショットの直列化・厳密な検証、状態の復元と整合確認)のどこかに、ステート数または国家数の2乗に比例する処理がある可能性がある。**改善候補**: 次の測定(保存・復元の工程別の計時)で内訳を出してから判断する。大きな最適化は今回の対象外。
- 1日の最大値は 2〜3ms(月次処理日)で、画面表示の1フレームを大きく超えない規模。ただし画面の描画・UIは含まない。

## 11. M4 への評価(閉鎖の提案。宣言ではない)

元設計(P32-003 §12)の M4 は「人口・施設・生産の接続」で、完了条件は「既存テスト群が新旧どちらでも合格」。P32-023 の整理では、検証用規模(3ステート・3国家)で本文は満たされているように読めるが、適用範囲が明記されていないため閉鎖の解釈はユーザー判断として残っていた。

今回の結果が加える根拠:

- 新ステート経済の経路が、合成の最大1000ステート(国家3または100)で、決定的に動き(同一条件の複数回・別プロセスで一致)、保存・再開後の継続が連続実行と各日一致する。
- 日次進行の時間は1000ステートでも 1日 0.08ms 程度で、規模に対しておおむね線形。時間上限(120秒)内で全ケースが完了した。

**閉鎖できる根拠(提案)**: 「検証用規模を超えた合成規模でも、経済経路の正しさ(決定性・保存再開)が保たれ、日次進行の時間が許容範囲に見える」ことが記録で言えるため、M4 の元設計の本文(新旧どちらでも動く・ステート数に対する性能懸念)について、閉鎖を検討できる状態になった。

**閉鎖前に残る条件・注意**:

1. 実規模(プロヴィンス数万・実データの人口/資源/施設分布)の測定は未実施。合成1000ステートはこれを保証しない。M4 の閉鎖を「合成規模までで十分」とするか「実規模データの用意後」とするかはユーザー判断。
2. 保存・復元の時間の増え方(§10)は、合成規模の範囲では許容できる絶対値(10秒以内)だが、実規模で問題になる可能性があり、内訳の測定が望ましい(性能を閉鎖条件に含めるかはユーザー判断)。
3. 位置施設の効果・建設条件、資源の枯渇、部分割譲・占領等の未決のゲームルールは、これまでどおり未決のまま(今回何も決めていない)。
4. 画面(UI)側の規模での動作(1000ステートの表示・一覧・保存パネル)は未確認。

**後続(M5〜M9)**: M5 補給連結性、M6 軍の位置・占領、M7 和平・領土移転・勝敗、M8 SaveGameV2、M9 本体の切替。いずれも未着手のまま。D11(旧V1の扱い)は未承認で、決めていない。

## 15. 環境依存テスト2件の修正と必須チェックの完了

### 15.1 原因の確認(実コード)

最初の全体テストで失敗した2件(`p32_020::the_session_view_never_writes_files`、`p32_021::the_build_ui_never_writes_files`)を、実コードから確認した。

- 両テストは、実際の `saves/` を読み(`fs::read_dir("saves")`)、最後に `saves/map_economy` が**存在しないこと**を主張していた。
- 画面のAppの保存先は `SaveLocationRes`(既定 `saves`)で、これは注入で差し替えられる。テストは差し替えずに既定の `saves` を使っていた。
- アプリ側は今回ファイルを書いていない: 失敗時点の `saves/map_economy/` の2ファイルは更新日が 2026-10-30(ユーザーのS3手動確認の日)で、全体テスト実行(2026-11-02)より前。ファイルの内容(SHA-256)も、テスト実行の前後で不変。さらに、アプリが書いていない根拠として、`saves/map_economy` を持たない一時ディレクトリでは同じテストが成功した(§14.2)。

### 15.2 修正方針と内容(テストのみ。製品コード・保存動作は変更していない)
