## 3. 保存・復元の実行経路と工程(実コードとの対応)

呼出関係: `EconomySession::save/load`(`map_session.rs`)→ `map_economy_file::save/load`(同じ関数)。ハーネスも同じ関数を呼ぶ。以下は**実際に存在する逐次処理だけ**を工程にしたもの。工程は互いに入れ子にならず(親子なし)、時間をそのまま足せる。

### 保存(`save_with_io_timed` → `save_body`)
| 工程名 | 実コード |
|---|---|
| `save.snapshot` | `MapEconomySimulation::snapshot`(`snapshot.rs`。内部で `context_id` を計算) |
| `save.identity` | `StaticIdentity::compute` + `to_saved`(`static_identity.rs`。21項目、地図全体の走査を含む) |
| `save.encode` | `encode`(`ron::ser::to_string_pretty`) |
| `save.verify_decode_header` / `save.verify_decode_body` | `decode`(書いた結果が読めることの検証)の、ヘッダー解析(`kind`・版の判定)と本体の解析 |
| `save.verify_compare` | 読み戻した値と元のスナップショット・識別情報の完全比較 |
| `save.target` | 名前と保存先の検証(`SaveLocation::target`。ディレクトリの実体確認を含む) |
| `save.existing_check` | 既存ファイルの確認(存在すれば読み込み+`decode`。今回の測定では存在しない) |
| `save.temp_create` / `save.write` / `save.sync` / `save.replace` | 一時ファイルの作成、書込+flush、`sync_all`、置換(`rename`) |

### 復元(`load_timed` → `examine` → `restore_timed`)
| 工程名 | 実コード |
|---|---|
| `load.target` / `load.read` | 保存先の検証 / `read_limited`(サイズ確認・読込・UTF-8検証) |
| `load.decode_header` / `load.decode_body` | `decode` のヘッダー解析と本体の解析 |
| `load.identity` | 復元先の静的入力からの `StaticIdentity::compute` |
| `load.judge` | 項目別の判定 `judge` |
| `restore.validate` | `validate_snapshot`(版・規則・`context_id` 照合、状態・国家の検証) |
| `restore.build_candidate` | `build_candidate`(候補の構築) |
| `restore.roundtrip_snapshot` / `restore.roundtrip_compare` / `restore.roundtrip_drop` | 候補から取り直したスナップショットの生成 / 入力との完全比較 / その破棄 |
| `restore.apply` | `*self = candidate`(旧状態の破棄を含む) |

### 繰り返されている処理(コードから分かる事実。今回は削除・統合していない)
- **全文の読み戻し解析**: 保存は `encode` の直後に同じ文章全体を `decode`(2回の解析)する(`save_body`)。復元は1回の `decode`。**`decode` はヘッダー用と本体用で、同じ文章を2回解析する**(`ron::from_str::<Header>` と `ron::from_str::<FileOwned>`)。したがって保存は文章を計4回、復元は計2回、先頭から解析する。
- **静的識別情報の生成**: 保存で1回、復元で1回(`inspect` でも1回)。21項目のうち複数が地図全セルを `sorted_cells` で並べ直す(`static_identity.rs` の `CellCoordinates`・`LandSet`・`WaterKinds` 等)。地図サイズに依存し、ステート数には依存しない。
- **スナップショット生成と `context_id`**: 保存で1回(`snapshot`)、復元で `validate_snapshot` の `context_id` 照合に1回、`roundtrip_snapshot`(スナップショット+`context_id`)に1回。
- **保存先の検証**: 保存は `target` と `existing_check` で `symlink_metadata` を重ねて呼ぶ。

## 4. 計時の実装と再実行

- 有効化: 呼出側が `Timing::on()` を渡して `save_timed` / `load_timed` を呼ぶ(通常API・通常起動は常に `Timing::off()`)。計時の結果は `Timing` にだけ入り、保存データ・経済状態・判定・戻り値には入らない(保存ファイルに計時の語が入らないこと、経済側のコードが計時を使わないことをテストで確認)。通常起動で計時ログ・ファイルは作らない(`phase_timing.rs` は出力もファイル操作も持たないことをテストで確認)。
- 計測範囲: 全体は関数の入口から出口まで。工程は直列で重ならない。**工程で覆っていない時間**(分岐・ループ・計時自体)は `uncovered` として別に記録した(§6: 全試行で 0.01〜0.5 ms で、全体の 0.01% 未満)。
- 結果の区別: `Success` / `Rejected`(互換性判定で拒否) / `Error`。拒否・エラーを成功として記録しない(テストで確認)。
- 再実行: `strategy_game/` で `cargo run -j 1 --release --bin economy_save_timing -- --series`(ケース×モードを別プロセスで逐次実行。各プロセス上限 120 秒+30 秒で強制終了し、成功以外が出たら以降へ進まない)。単独: `… -- --states 1000 --countries 3 --mode on --trials 3`。**直接 `target/release/economy_save_timing.exe` を起動すると、動的リンクの DLL が見つからず失敗する**(`series_attempt0_loader_error.txt`。測定ではない。`cargo run` で実行すること)。集計: `python -I aggregate.py series_run1.txt > tables_run1.md`。
- 保存先は試行ごとの一時ディレクトリ(`saves/` を含む場所は拒否)。測定後に自分が作ったファイルだけを削除する。

### 6.4 計時による追加負荷
外側から計った時間の「計時あり平均 − 計時なし平均」(ms。`tables_run1.md` 末尾): 100×3 は −1.1〜+0.9、300×3 は −5.6〜+8.5、1000×3 は −9.7〜+78.8、1000×100 は −189〜+143。符号が一定せず、各ケースの時間(最大約 10 秒)の 2% 未満で、プロセス間のばらつきの範囲内。計時は工程ごとに時計を2回読むだけ(保存で約 12、復元で約 12 工程。1回あたりマイクロ秒未満のオーダー)で、**追加負荷は検出できなかった**(負荷がゼロだとは主張しない)。細かい計測のための全件走査は追加していない。

P32-024(`810e151` の更新前の地図)の 1000×3: 保存 2417 ms / 復元 4360 ms / 765,581 B、1000×100: 保存 8789 / 復元 10655 ms / 1,248,977 B。今回の計時なし(試行平均): 1000×3 は保存約 3.6 秒(試行1 2.17 秒、試行2・3 約 4.3 秒)・復元約 4.1 秒・766,591 B、1000×100 は保存約 10.7 秒(試行1 7.4 秒、試行2・3 約 10.3 秒)・復元約 10.4 秒・1,251,733 B。**入力が同一ではない**(地図更新で陸セルが増え、合成入力が変わった。バイト数が異なる)ため、P32-024 の値とは比較せず、今回の計時なし測定を基準とする。大きさ・傾向(1000 ステートで数秒〜10 秒、ステート数に対し線形を超える)は同程度。
P32-024 の 1000×3 の保存 2417 ms は、今回の試行1 の値(2.17 秒)に近く、1回しか測っていなかった当時の測定は、試行1 の水準だった可能性がある(未検証の推測)。

## 9. 分析

### 9.1 測定で確認できた事実
1. **1000 ステートでは保存・復元の時間の 98.3〜99.4%(2.1〜10.4 秒)が「ヘッダー解析」工程**(保存の読み戻しの `decode` の1回目、復元の `decode` の1回目)。同じ文章を全項目で解析する本体解析は 6〜18 ms にすぎない。
2. 100→300→1000 の増加は、ほぼヘッダー解析によるもの。本体解析は文章量に比例(線形)、識別情報生成は一定(約 19 ms。1000 ステートの試行2以降は約 38 ms)。ヘッダー解析の 1 KB あたりの時間はサイズとともに増える(0.33 → 0.86 → 2.8 ms/KB)。
3. 他の工程(スナップショット生成、`encode`、ファイル書込・同期・置換、復元の検証・候補構築・往復確認・適用)は、すべて 1000 ステートでも 1 桁〜数十 ms 以下。ファイル入出力(`write`+`sync`+`replace`)は保存全体の 0.1% 未満。
4. 工程で覆っていない時間は全体の 0.01% 未満で、主要な時間は漏れなく工程に入っている。
5. 1000 ステートでは、試行1が試行2・3より速い(保存で約 2 倍、復元で約 1.2 倍)。**識別情報生成(地図だけに依存する処理)や `encode` まで同じ約 2 倍に遅くなっている**(19.6→38 ms、2.5→5.9 ms)。100・300 ステートでは起きない。
6. 計時の追加負荷は検出できなかった。計時なし/ありで、保存データ・復元状態・判定・継続は一致した。

### 9.2 コードから分かる事実(処理件数・計算量)
- 保存は文章全体を `decode` で再解析する(ヘッダー用と本体用の2回)。復元の `decode` も同じ2回。ヘッダー解析は `kind`・`format_version`・`version` だけを読み、`identity` と `snapshot` は `ron` の読み飛ばし(`deserialize_ignored_any` → `deserialize_any`)に任せる。
- 識別情報生成は地図全セル(96,760)を対象にし、ステート数には依存しない。

### 9.3 まだ未検証の原因仮説(本調査では確認していない)
- (H1)`ron` 0.12 の読み飛ばし(`deserialize_any` が構造体・タプルの種別を先読みする `check_struct_type` など)が、入れ子の深さや項目数に対して再走査を繰り返し、文章量に対して線形を超えて増える。**測定が示すのは「ヘッダー解析が文章量より速く増える」ことまでで、ライブラリ内部のどの処理が原因かは測っていない。**
- (H2)1000 ステートで試行2以降が約 2 倍遅くなる現象は、プロセス内のメモリ状態(前の試行の状態の保持・割り当ての断片化など)、または CPU の割り当て(ハイブリッド CPU の性能/効率コア)といった実行環境の要因かもしれない。**識別情報生成のような無関係な処理まで遅くなる**ため、解析処理固有の問題とは限らない。未検証。

### 9.4 結論と限界
- **確定していること**: 保存・復元の主要な時間は、読み戻し・読込時の `decode` のヘッダー解析工程に集中している(1000 ステートで 98% 以上)。識別情報生成・本体解析・ファイル入出力・検証・候補構築は主因ではない。
- **確定していないこと**: ヘッダー解析が遅い理由(H1)と、試行2以降が遅くなる理由(H2)。
- 限界: 合成シナリオ、6プロヴィンス/ステート、1台のハードウェア(Windows・i7-12700F)、ピークメモリ未測定、各ケース3試行(1000 ステートの傾向は 4 プロセスで再現したが、平均だけで断定していない)。実データ・全世界規模では未測定。P32-024 の比較は入力の差のため行っていない。
- TOCTOU、クラッシュ・電源断耐性、シンボリックリンク拒否の実環境確認は、**今回の計時追加で解決したとは扱わない**(P32-023 §8 のまま)。
