## 3. 集約規則(P32-029 §4.3 の `Full/Partial/None` では不足したため、組み合わせを表にした)
件数: `total = reachable + unreachable(確定: 通行不可 + 経路なし) + unknown + not_applicable`(不変条件。テストで全ケース確認)。

| 条件(上から最初に当てはまるもの) | 区分 |
|---|---|
| `total == 0`(所属が空) | 所属なし(`Empty`。**全域到達にしない**) |
| `not_applicable == total` | 対象外 |
| `reachable == total` | 全域到達(`Full`) |
| `reachable > 0` | 一部到達(`Partial`。残りが不明・不能・対象外のどれかは件数で見る) |
| `unknown > 0` | 不明(**到達不能へ丸めない**) |
| それ以外 | 到達不能(判定できた所属が、すべて確定した到達不能) |

- ステート未所属のプロヴィンスはどのステートの件数にも加えず、`unassigned` として別に持つ(ステート合計+未所属=ノード数を検証)。明示的に許可すれば経路には使える(P32-030 の挙動を要約が変えない)。
- 出力は `MapStateId` 昇順。所属・通行条件・起点の列挙順に依存しない(テストで確認)。`ProvinceId`/`MapStateId`/旧 `StateId` は数値一致で変換しない(同じ数値が混在するケースをテスト)。別グラフの `Reach` は `Err`。

## 7. 測定の限界
- 1台・3試行・他プロセス共存。絶対値は目安で、桁と内訳の比を見る材料。メモリのピークは測っていない。
- 1陸セル=1プロヴィンスの理想化。実際の全世界の区画は節点数・辺数が異なり得る(現在の辺数は約2.8/節点)。
- 探索主体の領域・起点は負荷の形を作る入力で、現実の国家配置ではない。heavy は最大成分(約17.2k)までしか着けない(35k全体を舐める条件ではない)。
- 準備は「毎日、全主体の通行集合を最初から作り直す」最悪側(差分更新は測っていない)。解放は結果の `drop`。ゲーム全体(描画・経済)と並走した場合の影響は測っていない。
- `reach` は毎回 ID 配列とグラフの署名を複製し、通行条件は `BTreeSet`(O(log n))で引く。**未最適化の素朴な実装の値**で、下限ではない。

## 8. D10 への材料と提案(確定ではない)
**提案: プロヴィンス単位の探索を維持できそう。** 根拠: 35kノードの全主体・1巡が、最悪側(100主体・各17k到達)でも約0.25〜0.28秒、30主体で約0.08〜0.09秒、3主体で約0.01秒(未最適化)。ステート単位だけに縮約すると内部の分断が見えなくなる(§5、P32-029 §3)ので、P単位で判定してステートへ集約する方針と矛盾しない。

| 方式 | 費用(本測定) | 前提 |
|---|---|---|
| 毎日、全主体を再計算 | 3主体 約5〜9 ms / 30主体 約28〜91 ms / 100主体 約80〜282 ms | 1ゲーム日の実時間の予算が決まっていない。100主体の高負荷は約0.28秒で、1日を短く(例: 1秒未満)する場合は他処理と合わせた予算の確認が必要 |
| 入力(通行集合・起点・所属)が変わった主体だけ再計算 | 1主体あたり 約0.8 ms(split)〜2.8 ms(heavy。準備・探索・集約・解放の合計 ÷ 主体数) × 変化した主体数 | 入力の変更を検出する仕組み(主体ごとの版・dirty 管理)が要る。支配が日々大きく動く時期(M6/M7)には、毎日再計算に近づく |

追加の観察: split では**集約が日合計の約4割**(全ノードを主体ごとに数えるため。到達件数に比例せず O(ノード数×主体数))、heavy では探索6割・準備2割。最適化の候補(今回は実施しない): 通行条件を `BTreeSet` からビット列へ、`Reach` の ID 配列の複製の削減、集約を「到達・不明・通行不可の差分だけ」にする。判断(D10)・日次/変更時の方針・予算の閾値は、ユーザーの決定事項として残す。
