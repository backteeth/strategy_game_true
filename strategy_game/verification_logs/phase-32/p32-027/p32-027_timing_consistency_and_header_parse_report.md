## 2. 計時の対応の確認(P32-026 の「保存全体 7427 ms、ヘッダー解析 7439 ms」)

### 2.1 原因: 別の呼出・別のプロセスの値を並べた報告の誤り(測定の誤りではない)
- P32-026 の最終報告の表で「保存の全体 7,427 ms」と書いた値は、**パス1(計時なし、`mode=off`)の試行1の、外側から計った保存の時間**(`TRIAL … mode=off … save_wall_ms=7427.4`)。一方「ヘッダー解析 7,439 ms」は、**計時ありの2つのパス(パス2: 7379.4 ms とパス3: 7498.5 ms)の試行1のヘッダー解析工程の平均**(7438.9)。**別のプロセス・別の呼出の値**を同じ行に並べたため、ヘッダー解析が全体を上回って見えた。
- 同じ構造の混在が、P32-026 報告書 §6.3 の表にもある(「保存の全体」列は計時なし平均、ヘッダー解析列は計時あり平均)。そこの「計時なし平均=計時ありの全体と整合」の記述は、別の呼出どうしの近似であって、同一呼出の包含関係の確認ではなかった。
- 単位はすべて ms(`Duration` を `as_secs_f64() * 1000`)で、丸めは表示のみ(`{:.3}` / `{:.1}`)。列の対応の誤りは、上の別呼出の混在だけ。

### 2.2 生ログの確認(`p32-026/check_consistency.py`、`series_run1.txt`)
- **同じ呼出ごと**に、(a) 全体 = 工程の合計 + 覆っていない時間、(b) ヘッダー解析 ≤ 全体、(c) 全体 ≤ 外側から計った時間、(d) 工程の合計 ≈ 各工程の合計、を検査: **計時ありの全48呼出で違反0**。
- 全体時間は、関数の入口〜出口(読み戻し `decode` を含む)で、保存では工程が互いに入れ子にならないため、工程の時間を足してよい。**読み戻しは保存の呼出の中の工程**(`save.verify_decode_*`)で、別の呼出ではない。
- 工程時間は呼出ごとに新しい `Timing` に記録される: 計時ありの全 576 工程記録の `calls=1`(複数呼出の累積なし、試行をまたいだ蓄積なし)。
- 1000 ステートの同一呼出ごとのヘッダー解析の割合(ヘッダー解析 ÷ **同じ呼出の全体**): P32-026 の計時ありパスで 1000×3: 98.25〜98.59%(12呼出)、1000×100: 99.30〜99.38%(12呼出)。P32-026 が書いた「98.3〜99.4%」は、**この同一呼出の割合の範囲と整合する**(結論は変わらない。ただし書いた値の根拠は混在した平均だったため、本節の同一呼出の値で置き換える)。

### 2.3 修正と再測定
- 修正: 計測の出力に、同じ呼出の整合性の行 `CHECK`(工程の合計 ≤ 全体 ≤ 外側の時間、最大の工程 ≤ 全体)を追加し、テストで確認する。呼出を区別する識別(`case / mode / trial / op=save|restore`)は既存の `TOTAL` / `SPAN` / `TRIAL` 行にあり、読み戻しは保存の呼出内の工程として区別されている(`inspect` は今回の測定の対象外)。
- 再測定(影響するケース 1000×3 と 1000×100 のみ、計時なし→あり。`series_recheck.txt`): 全プロセス成功、`CHECK` 12行すべて true。1000×3 の保存 2113.6 / 2165.9 / 2142.9 ms(ヘッダー解析 2083.9 / 2132.7 / 2110.9)、1000×100 の保存 5069 ms 前後(ヘッダー解析 5032 / 4994 / 5011)。**ヘッダー解析 ÷ 同一呼出の全体は 98.20〜98.59%(1000×3)、99.11〜99.33%(1000×100)**。
- **注意**: この再測定の絶対時間は、P32-026 より速い(1000×100 の保存 7.4〜10.3 秒 → 5.0 秒)。時間が環境(実行時)によって約 2 倍変わる現象が原因で、§5 で扱う。

**事実**: (1) **数値(整数・小数)を含む要素を多数並べた列は、量を2倍にすると約4倍**(2乗)。(2) 識別子・文字列だけの列は線形。(3) 入れ子の深さそのものではなく**数値の個数**が効いている(深さ24の入れ子でも、数値が項目あたり1つなら小さい)。(4) 数値の列の間に、`..` を含む文字列を1つ挟むだけで、同じバイト数のまま線形になる。製品の保存文章は、状態ごとの建物レベル・人口などの**数値**を多数含み、状態ごとの列として並ぶので、この条件に当たる。

### 3.5 原因(根拠つき)
**実測の根拠**: §3.4(数値を含む列だけが2乗、識別子・文字列は線形、数値の間に `".."` を挟むと線形に戻る)、§3.2・3.3(時間は状態の列にあり、型つきの本体解析は線形で速い)。
**ソースの根拠**(`ron` 0.12.2、`parse.rs`): 全文の読み飛ばしは `deserialize_ignored_any` → `deserialize_any`(`de/mod.rs`)に入り、数値は `any_number` → `next_bytes_is_float` を通る。そこ(`parse.rs:1040`)で `self.src()[skip..].find("..")` が、**現在位置から文章の残り全体**を `..`(範囲演算子)を探して走査する。数値を1つ読むたびに残りの全文を走査するため、数値の個数 × 残りの長さに比例して増える(2乗)。残りに `..` が無い限り、毎回、文章の末尾まで走査する。型つきの解析(`integer()` を直接呼ぶ)はこの経路を通らないため線形。
**結論**: 「全文の読み飛ばしが支配的」で、その中の具体的な原因は、**`ron` の読み飛ばしにおける数値ごとの残り全文の `..` 検索**と判断する(実測とソースの両方で裏づけ)。ただし、`ron` 内部の他の処理が寄与している可能性を完全には排除していない(`..` を挟む実験で、同じ数値の個数でなくバイト数を揃えたため、数値の個数は約半分に減っている点も制約)。

## 5. 約 2 倍の速度差(環境要因の切り分け)

観測した事実:
| 状況 | 1000×3 のヘッダー解析 |
|---|---|
| P32-026 の計時プロセス(保存の試行1 / 試行2・3) | 約 2.1〜2.2 秒 / 約 4.3 秒 |
| P32-027 の再測定(保存の試行1・2・3) | 約 2.1 秒(全試行) |
| `economy_parse_compare` の製品文章(新しいプロセス3回) | 約 4.3〜4.4 秒(全試行) |
| `variants`(別のプロセス) | 約 2.1〜2.3 秒 |
| **プロセスのCPU割り当てを固定**: マスク 0xFFFF(論理 0〜15)/ 0xF0000(論理 16〜19)/ 固定なし(0xFFFFF) | **約 2.13〜2.22 秒 / 約 4.14〜4.38 秒 / 約 4.26〜4.35 秒**(各3試行、`affinity_*.txt`) |

- **事実**: 同じ文章・同じコードでも、プロセスごと(および1つのプロセスの途中)で約 2 倍の違いが出る。試行番号やメモリとは関係せず、**CPU の割り当てを固定すると、2 倍の差が再現した**(論理 0〜15 で速く、16〜19 で遅い。固定なしの実行は遅い側だった)。解析と無関係な処理(識別情報生成、`encode`)も同じ比率で変わっていた(P32-026)。
- **仮説(未検証)**: 実行環境(i7-12700F はハイブリッド CPU で、高性能コアと効率コアがある)での、実行されるコアの違い。**論理プロセッサ 0〜15 が高性能コア、16〜19 が効率コアという対応は、今回確認していない仮定**。観測できたのは、割り当ての固定と速度差が対応していることまで。クロック・電力設定など他の要因は排除していない。
- 帰結: P32-026 の「試行1が速い」という記述は、試行の性質ではなく、環境の状態によるもの。P32-026 の絶対値(特に1000 ステート)は、この環境差を含む。ステート数に対する**増え方の比較**(§3)は、同じプロセス・同じ状態の中で行った値だけを使い、環境差が混ざる比較をしていない。

## 10. 次に推奨する最適化案(1件。今回は実装していない)

**対象**: `map_economy_file::decode`(`decode_timed` の共通本体)のヘッダー段階。`Header` の解析が、文章全体を `ron` の読み飛ばし(`deserialize_ignored_any`)で読んでいる処理。

**案**: 先に「型つきの完全解析(本体、現在の `FileOwned`)」を1回だけ試し、**成功したときだけ**、現在と同じ順序で `kind`・`format_version` の判定を行って返す。型つきの完全解析が失敗したとき(旧V1、別の kind、非対応の版、壊れた文章、重複・未知のフィールド、欠落など、**成功ではないすべての入力**)は、**現在のヘッダー段階+本体段階の処理をそのまま**実行して、現在と同じ判定・拒否理由を返す(フォールバック)。
- 削減できる処理: 正常な保存の読み込み・読み戻しで、ヘッダー段階の全文読み飛ばし(1000 ステートで 2〜10 秒、保存・復元の 98% 以上)。保存の読み戻し検証(`save` 内の `decode`)と復元の `decode` の両方に効く。
- 根拠: 型つきの本体解析が線形で速いこと(§3.2: 1000×3 で 6〜14 ms)。
- **未確認点**: (1) フォールバックを含めて、現在と判定・拒否理由・拒否順が同一であること(成功した型つき解析の後の `kind`・版の判定が、現在のヘッダー判定と同じ結果になるか。`FileOwned` が `kind` / `format_version` を持つ場合の扱い、`implicit_some` の違い、複数フィールド・コメント・空白・順序違い・重複の扱い)。(2) 実際の削減量(1000 ステートでの保存・復元の全体)。(3) 型つき解析が、成功する入力の副作用(メモリ使用量)で不利にならないこと。
- 保存形式: 変更しない(読み方だけ)。`kind` と版の定義、未知フィールド拒否、厳密な本体、V1 の非廃止・非変換は維持。
- 正常・旧V1・非対応版・破損入力への影響: 設計上、成功の経路だけが新しく、他はすべて現在の処理へ戻るため、**判定が変わらないこと**を目標にする。変わりうる箇所は、「型つきの完全解析が成功するが、現在はヘッダー段階で拒否される」入力(例: `kind` が違うが本体が型どおりに読める、版が違うが本体が現行の形)。この場合も、成功後に現在と同じ `kind`・版の判定を同じ順序で行えば、同じ拒否になる。
- 必要な同等性検証: 現在の `decode` と新しい `decode` を、(a) 代表の正常な保存(複数規模)、(b) 旧V1の形、別の kind、非対応の版(形式1・99)、`kind` 欠落、(c) 壊れた文章(途中で終わる・構文が壊れる・UTF-8 でない)、(d) 重複フィールド・未知フィールド・必須項目の欠落・順序違い・コメント・空白、(e) 後半だけが壊れた文章(kind が正しい/誤り)、の入力集合で比較し、`Ok` の中身(`DecodedFile` の完全一致)と `Err` の種類・メッセージが**完全に一致**することを自動テストにする。`save` / `load` / `inspect` の既存テスト(拒否理由・状態不変・ファイル不変)がそのまま通ること。
- **採らない案**(文章の先頭だけを読んで `kind` と版を取る案): `kind` と版は RON の構造体のフィールドで、順序・重複・コメントを含む任意の位置に置けるため、先頭の部分読みでは確実に取れない。仮に取れても、**後半が壊れている文章**で、現在は「構文エラー(`Malformed`)」と判定されるものが、先頭だけを読む方法では「別の kind」「非対応の版」と判定され、**拒否の種類と順序が変わりうる**。また、後半の構文と内容は、結局、全文の型つきの解析まで検証されないため、先頭だけの読みでは保存全体の検証を保証できない。上の案(型つきの完全解析を先に試し、失敗したら現在の処理)は、全文の構文・内容の検証を現在と同じ段階(本体の型つき解析)で保証し、判定と拒否順の変化を、フォールバックで避ける。
- `ron` を更新して修正する案(`..` 検索を直す)は、依存の更新にあたるため、今回の方針(依存・Rust を更新しない)の範囲外として扱う。
