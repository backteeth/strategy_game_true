## 4. 保存対象と再導出対象
**保存(スナップショット)**: 日付(最後に処理を完了した日)/ステート: 人口・雇用(就業・失業)・物流の3値・生活水準・不満度・施設レベル・稼働率(月次で確定した値を式で再計算しない)/国家: 国庫・税率・人的資源2種・備蓄(全9種)・月次損益3値・経済状態・建設キュー(識別子・対象・施設・目標レベル・進捗・必要進捗・**支払済み費用**・状態)・`next_order_seq`・`order_log`(全件)・AI の `dirty`・判断理由・`last_monthly_evaluation_day`・3つの履歴(標本)。
**再導出/引き継ぎ(保存しない)**: 資源設定(`resource_setup`)・鉱床・`workforce_ratio`・`base_logistics_capacity`・国家のステート集合・AI国家か否か・軍事入力 → 復元先の集約から引き継ぐ。出力ログ(`DayReport`・`AiEvaluation`)は保存しない。
**漏れの防止**: 候補の構築は `MapStateEconomy`/`ScenarioCountry` を**全項目を明示した構造体リテラル**で作る(項目の追加でコンパイルが止まる)。さらに「100日進んだ集約へ開始時のスナップショットを復元すると、開始時の集約と完全一致する」テストが、保存し忘れた動的項目を検出する。

## 5. 保存可能な時点と日付の意味
- 保存可能: **日次処理が完了し、次の日の処理を始めていない時点**(日と日の間)。月が変わった日でも、月次経済・履歴の記録・AI評価は `run_day` の中で完了している。`run_day` の途中は対象外(外から取得する手段が無い)。
- **日付 = 最後に処理を完了した日**。復元後の最初の `advance_day` は翌日を処理する(テスト: 開始時に復元→最初の処理日は1800/01/02。連続実行の結果と一致)。二重実行も飛ばしも起きない。
- 手動の注文・取消しは日と日の間に呼ばれるため、取得は注文の前後どちらでも整合する。

## 6. 同一コンテキストの制約
- 復元先は「同じ検証済み静的入力から作った集約」。スナップショットの `context`(FNV-1a 64bit)が、復元先の集約の静的入力(地理の5種の識別情報・各ステートの所属プロヴィンス・静的値・鉱床・資源設定・国家ラベル/AI/担当ステート/軍事入力・建物定義全項目)から計算した値と一致しなければ `ContextMismatch` で拒否する。さらに `section_version`・`ECONOMY_RULES_REVISION`(経済計算の規則の改訂番号。式・定数を変えたら手で上げる)が一致し、ステート・国家の集合と順序が復元先と**完全一致**であることも要求する。
- テスト: 別のシナリオ、資源定義の変種(1プロヴィンスの設定を外す)、建物定義の変更(Mineの費用+1)のいずれの復元先へも、**同じIDがあっても**拒否される。
- **これは内部の同一性確認であり、外部ファイルの署名検証(P32-017)の代替ではない。外部から読んだ値を無条件に受け入れるAPIではなく、ファイルI/Oも提供しない。** 外部署名検証は未実装であることを、モジュールのドキュメントに明記した。

## 7. 実行時状態専用の検証(入力の検証との区別)
- 拒否しない(実行中に正当に生じうる): 生活水準・不満度が (0,1] の値(入力用の「旧スケール曖昧」規則は使わない)、完成保留中の注文の**超過進捗**(有限・非負のみ要求)、**赤字の国庫**(有限であればよい)。
- 拒否する: 非有限の数値、範囲外(生活水準・不満度 0〜100、税率 0〜1、備蓄 ≥ 0、物流値 ≥ 0)、備蓄の種類の欠落/重複、存在しないステート・建物、ステート/国家の集合・順序の不一致、AI国家か否かの不一致、不正な日付(月・日・年)。
- 注文: 識別子の重複/国家不一致/`seq` が 1..`next_order_seq` の範囲外、キューとログに現れる連番がちょうど `1..next_order_seq` を過不足なく覆うこと、キューとログの重複、(ステート,施設)の重複、対象ステートが国家の担当に含まれること、建物の定義、`target_level == 現在の施設レベル+1`(**完成済みの注文がキューに残っている=再追加の兆候を拒否**)、進捗/必要進捗/支払済み費用の値。支払済み費用は**保存値**をそのまま使い、現在の建設費から再計算しない(テスト: 123.0 を保存→復元→取消しの返金が 61.5)。
- 実際に到達する状態で誤って拒否しないことは、**5つのシナリオの300日の全日**(各日のスナップショットを別集約へ復元)で確認した。

## 8. 履歴と注文識別子の復元
- 履歴: 標本は非公開フィールドで、無検証の `Deserialize` や代入では復元しない。各履歴に `from_samples`(月 1..=12、暦順に厳密な昇順、窓幅4以下)を追加し、復元時はこれを通す。加えて「最後の標本の年月 ≤ 保存日付の年月」「`last_monthly_evaluation_day` ≤ 保存日付」を検証(未来の標本は以後の `record` を拒否し続けるため)。履歴を消した保存値は検証を通るが、**連続実行と判断・結果が変わる**ことを対照テストで確認した(=保存が必須)。
- 注文識別子: `next_order_seq`(高水位標)と `order_log` を復元する。復元後の新規注文の識別子は保存した `next_order_seq` から続き、キュー・ログのどれとも衝突しない(テスト)。完成・取消し済みの識別子の取消しは `AlreadyCompleted`/`AlreadyCancelled` のまま拒否され、返金されない。

## 9. 失敗時の非変更
`restore` は 検証 → 候補の新規構築(`restore_candidate`) → 候補から取り直したスナップショットが入力と一致することの確認 → 成功時のみ **1回の代入**で置換、の順。失敗時は `self` に一切触れない。テストでは、日付・全ステート・全国家(国庫・キュー・ログ・履歴を含む)を持つ集約の `clone` と、失敗後の集約を完全比較した(版・規則・コンテキスト・日付・ステート/国家の集合・数値・注文・履歴の各不正入力、計60種弱の変種)。復元は、注文の受付・支払い・完成・取消し・返金・月次経済・AIの行動を**呼ばない**(「開始時のスナップショットを100日進んだ集約へ復元すると開始時と完全一致」「復元前後で国庫が変わらず費用が再徴収されない」で確認)。
