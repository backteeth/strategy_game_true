## 1. 設計の対象(AとBの区別)

| | 内容 | 本書での扱い |

## 2. 実コードの調査結果(設計の根拠)

### 2.1 実行時状態の持ち主と更新処理
- `MapStateEconomyRegistry`(`economy/map_state.rs`): `BTreeMap<MapStateId, MapStateEconomy>` と `resource_setup`(資源設定の接続状況)。
- `ScenarioCountry`(同 :773): 国庫・税率・人的資源・備蓄・担当ステート・月次の損益・**建設キュー・`next_order_seq`・`order_log`・経済状態・AI状態**。
- 日付は**レジストリに含まれず**、呼び出し側が `SimDate`(年・月・日。端数なし)を持つ(`manual_script.rs`・CLI・テストは開始日 1800/01/01 から `SimDate::next` で進める)。
- 1日の処理 `run_day`(:1387)は同期的な1関数で、順序は 建設の進捗・完成 → (月が変わった日のみ)月次経済+AI履歴の記録 → AI国家の評価。**途中で外へ制御を返さない**ので、呼び出しの間だけが整合した状態になる。
- 手動の注文・取消し(`request_build`・`cancel_order`)は、`run_day`と`run_day`の間に呼ばれる(`manual_script`は「その日数が経過した後、次の日の処理の前」)。
- 月次経済で更新される値: 人口、雇用、物流、生活水準、不満度、稼働率、備蓄、国庫、人的資源、国家の損益、経済状態。建設完成で更新される値: 施設レベル。**不変**: `workforce_ratio`・`base_logistics_capacity`(新経路で書き換える処理は無い)、鉱床(`resource_deposits`。`attach_province_resources` で接続した値。新経路の処理は `discovered`・`development_level`・産出量を変更しない。旧経路の `debug`・`research` だけが `discovered = true` にする)。

### 2.2 旧V1セーブ(`save/*`、`saves/savegame_v1.ron`)
- `SaveGameV1`(`save/dto.rs`)は旧28州の世界に結び付いている(`states: Vec<StateData>`、師団の `current_state`、戦争の占領州、前線、`capital_state_id` など)。`version` は `SAVE_FORMAT_VERSION_V1 = 1`。
- 読込(`save/read.rs`): `SaveVersionHeader{version}` だけを先に読み、`version != 1` は `UnsupportedVersion`。その後に全体を解析し、`validate.rs` で参照整合性を検証してから `apply.rs` が Prepare→Commit の二段階でWorldへ適用する。**検証と適用が分かれている**(失敗してもWorldは変わらない)。
- 書込(`save/write.rs`): 一時ファイル `<final>.tmp` へ書き、`rename` で置換する。失敗時は既存ファイルを壊さない(テスト済み)。
- **保存先**: 既定は `saves/savegame_v1.ron` の**単一スロット**。起動直後の「続きから」(`ui::country_selection`)がこのスロットを読む。`saves/savegame_v1.ron` は git で追跡されている(SHA-256 `98b2175639666094dc9c1f11127de1aca740d81b72acbff7c5f1d9a26564130` を確認。この設計では触れない)。
- **重要な含意**: 新経路の保存を同じスロットへ書くと、既存のV1セーブを上書きする。逆に、新形式のファイルをV1のスロットへ置くと V1 の読込は `UnsupportedVersion` で拒否する。**新旧を保存先で分けないと、取り違えが起きる**。
- 先例: V1は `SupplyProductionHistory`・`IronShortageHistory`・`FactoryStarvationHistory` を `#[serde(default)]` の追加フィールドとして**既に保存している**(旧経路のAI履歴の永続化)。履歴の型は `Serialize/Deserialize` 済みで、窓幅(`SUPPLY_HISTORY_WINDOW`・`IRON_SHORTAGE_WINDOW`・`FACTORY_STARVATION_WINDOW` はいずれも4。P32-015 で `SUPPLY_HISTORY_WINDOW = 4`・`IRON_SHORTAGE_WINDOW = 4`・`FACTORY_STARVATION_WINDOW = 4` を再確認し訂正)も定義済み。ただし新経路の履歴は `ScenarioAi.history` に**実行時のみ**で持ち、永続化していない(P32-012 の記録どおり)。

### 2.3 P32-003 の旧セーブ方針の位置づけ(提案か承認済みか)
- P32-003 §10 は「M9で `SaveGameV2` を導入し、**V1は明示的に非対応**にする」と**提案**し、§11 の D11 に「要判断」(推奨: 明示的に非対応)と記した。
- その後の報告(P32-004〜013)は一貫して「旧セーブ/V2 方針」を**未決のまま維持**と書いている。承認の記録は見つからなかった。→ **D11は提案段階で、ユーザー承認済みではない**。本書はそれを前提とせず、V1を非対応にする・上書きする・黙って互換を失わせる案を採らない(§8)。
- 承認済みの関連事項: P32-007 の「人口・雇用・施設はステート単位、資源の所在地はプロヴィンス単位、位置施設はプロヴィンス単位」。`§15` に追記済み。

## 3. 形式の比較と推奨

### 3.1 3案
| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **P** 独立した経済検証用の形式 | 新経路専用のファイル。`kind`・版・保存先がV1と別 | V1に一切触れない。Bや軍・戦争の未決に依存しない。再開一致の検証にすぐ使える | Bができたとき、取り込み経路が別途必要 |
| **Q** 将来のゲーム用形式(`SaveGameV2`)の一部としてだけ設計 | Bの一部分として設計 | 二重化しない | Bの前提(軍・所有・時計・旧セーブ方針)が未決で、今は作れない。検証が遅れる |
| **R** `SaveGameV1` へ新経路のフィールドを追加 | 既存形式へ追加 | 実装が少ない | V1は旧28州の世界に結び付く。新旧が1ファイルに混在し、V1検証(110箇所のStateId検証)と矛盾する。旧セーブを事実上変える。**不採用** |

### 3.2 推奨: **P を、Bが取り込める節として設計する**
- 動的状態を1つの自己完結したDTO(仮称 `MapEconomyState`、節の版 `section_version`)にまとめる。
- 当面は**封筒**(envelope)に入れた独立ファイルとして保存する。封筒は `kind`(新旧取り違え防止)・`format_version`・静的データの参照(§5)・節の本体を持つ。
- Bの段階では、同じDTOを `SaveGameV2` の1フィールドとして**変更なしで**取り込める(封筒のうち世界参照だけがV2全体の参照へ統合される)。
- V1とは**別の保存先・別の拡張子・別の `kind`** にする(§7)。

### 3.3 版管理
- `format_version` は**完全一致のみ受理**(V1・`manual_script` と同じ方針)。未対応の版は拒否し、黙って読まない。
- 互換の規則: 任意項目の**追加**は `#[serde(default)]` で版を上げずに可能(ただし既定値が「過去の保存と同じ意味」になる場合のみ)。意味の変更・削除・必須項目の追加は版を上げる。
- 先に `kind` と `format_version` だけを読む最小ヘッダー(V1の `SaveVersionHeader` と同じ手法)で判定し、一致しなければ本体を解析しない。
- RONの制約: 128bit整数が使えない(履歴・軍事入力は既に64bitで設計済み)。非有限の浮動小数は読込時に検出して拒否する。`HashMap` は列挙順が不定なので、保存時は**キー昇順のリスト/BTreeMap**にして出力を決定的にする。

## 4. 保存対象の棚卸し(対応表)

凡例: 正本=復元後にその値が唯一の正しい値になるもの。「保存」=ファイルへ書く。「再導出」=読込時に静的データ(や他の保存値)から再計算できるので書かない。

### 4.1 時間・処理段階
| 項目 | 現状の置き場 | 保存 | 再導出 | 復元時の依存・条件 |
|---|---|---|---|---|
| 現在日付(最後に完了した日) | 呼び出し側の `SimDate`(レジストリ外) | **保存** | 不可 | 月 1..=12、日 1..=`days_in_month`、年は妥当な範囲。AIの周期は `date.day_number()` と国家ラベルから導出される |
| 処理段階 | 無い(`run_day` は途中で止まらない) | **保存しない**(段階は「日と日の間」に固定) | — | §6 |
| 日の端数(accumulator) | 新経路に無い | 対象外(Bの時計) | — | |
| `DayReport`・`ManualLogEntry`・CLIの出力 | 出力ログ | **保存しない** | 再生で再現 | 実行継続に不要。検証の比較用 |

### 4.5 注文識別子・AI状態・履歴
| 項目 | 保存 | 理由 |
|---|---|---|
| `next_order_seq`(国家ごと) | **必須** | IDの**高水位標**。これがあれば、過去の注文を1件も保存しなくても識別子の再利用・衝突は起きない(`next_province_id` と同じ設計) |
| `order_log`(完了/取消しの終わり方) | **保存を推奨**(§5.2) | 二重処理の防止には**不要**(§5.1)。API上の拒否理由(`AlreadyCompleted`/`AlreadyCancelled`/`NoSuchOrder`)を保つために使う |
| `ScenarioAi.dirty` | **保存** | 初回評価の有無を決める。保存しないとロード直後に周期外の評価が走り、連続実行と判断の時期がずれる |
| `ScenarioAi.last_decision_reason` | **保存**(情報) | 判断には使われない |
| `ScenarioAi.last_monthly_evaluation_day` | **保存**(情報) | 新経路の判断には使われない(書くだけ)。往復一致のために保存 |
| `ScenarioAi.history`(3つの履歴: 供給・Iron不足・Factory飢餓) | **必須** | 窓内の月次標本。保存しないとIron継続不足(窓4か月)などの条件が「窓が再び揃うまで」判断されず、連続実行と**結果が変わる** |
| 履歴の整合性 | — | 標本は**年月の昇順・重複なし**、個数は窓幅以下、月 1..=12、**最後の標本の年月 ≤ 保存日付の年月**(未来の標本があると、以後の `record` が「過去の月」として拒否され続ける)。標本のフィールドは非公開で、`Deserialize` は `record` の不変条件を通らないため、**検証付きの復元関数が必要**(再生に `record` を使うとIronの`unmet_milli`の丸めが再現しないので不採用) |
| AI国家でない国家 | `ai` なし | 履歴を持たない |

| ステート所属(`StateLayoutFile`) | ゲーム側 | 手編集 | **所属の署名**(新規、または `membership_signature` の公開)を保存 |
| 資源定義(プロヴィンス別) | `province_resources*.ron` | 手編集 | `resources_signature`(公開)を保存。有効な資源ファイルの変種(例: `omit_resource_provinces`)は「実効の定義」の署名になる |
| 位置施設定義 | `province_facilities.ron` | 手編集 | **現状、経済の実行状態に影響しない**(効果は未実装)。保存の対象外。効果を実装する時点で署名を追加(予約欄 `location_facilities: None`) |
| 建物定義(費用・必要進捗・労働・上限) | `buildings.ron` | 手編集 | **署名(新規)**。ただし注文の `paid_cost`・`required_progress` は注文自体が持つ |
| 経済の定数・計算式 | コード | ビルドで変わる | **手動で上げる `economy_rules_revision`** を保存(コードのハッシュは取れない) |
| シナリオの構造 | `economy_scenario*.ron` | 手編集 | **構造署名(新規)**: 国家ラベル・`ai_controlled`・国家のステート集合・ステート集合・`workforce_ratio`/`base_logistics_capacity`・直接指定の鉱床・`military` 入力。**初期値(人口・国庫など)は含めない**(保存側が上書きする値なので、バランス調整で保存が無効にならない) |

### 4.7 「保存する」と「複製しない」の線引き
- 保存するのは**実行中に変わる値と、変わった結果でしか得られない値**(月次で確定した派生値、履歴、識別子の高水位標)だけ。
- 実行中に変わらない定義(資源、施設定義、位置施設、所属、地理)は**参照(署名)**で束縛し、コピーしない。コピーすると正本が2つになり、アセットの修正が既存セーブに反映されない/矛盾する。

## 5. 識別子・再実行防止・静的データとの照合

### 5.1 識別子の扱い
- **ProvinceId と MapStateId**: 保存データのキーは `MapStateId` のみ(プロヴィンスは持たない)。復元時に、各 `MapStateId` が現在の `WorldModel` に存在し、**所属の署名が保存時と一致する**ことを確認する。数値が存在するだけでは「同じ土地」とは見なさない(IDの意味が変わった場合は所属の署名が不一致になる)。`ProvinceId` は廃止IDの再利用禁止(高水位標・`retired`)が既に保証している。
- **旧 `StateId` と `MapStateId` は数値で変換しない**(既存方針)。保存・復元のどちらにも変換を持ち込まない。
- **国家ラベル**: シナリオ内だけで通用する識別子(旧 `CountryId` とは別)。保存の安定性は**シナリオの構造署名**が保証する(ラベル集合・各ラベルの `ai_controlled`・担当ステート)。ラベルが増減・付け替えされた場合は署名不一致で拒否し、**ラベルを別の国家へ割り当て直さない**。重複ラベルは拒否。将来ラベルが実際の国家IDに置き換わる場合は、保存形式の版を上げ、明示的な移行にする。
- **注文識別子 `ConstructionOrderId{country: ラベル, seq}`**: 保存すれば「実行時のみ有効」ではなくなる。**再利用・衝突を防ぐために必須なのは国家ごとの `next_order_seq` だけ**。理由: 識別子は `seq` が単調増加で再利用されず、`seq < next_order_seq` の注文は「キューにある」または「終わっている」のどちらか。ロード時に `next_order_seq` をそのまま復元すれば、以後に発行される識別子は過去のいずれとも衝突しない。**過去の全注文を永久保存する必要は無い**。
- 二重処理の防止は**構造的**に成り立つ(識別子の保存に依存しない):
  - 完成: 完成した注文は `advance_construction_queue` が**キューから外す**ので、保存時のキューに無く、施設レベルは完成後の値で保存される。復元は `place_order`・`on_complete` を呼ばない。
  - 取消し: 返金は `cancel_order` の中の「キューから外す」と同じ処理でのみ発生する。外した注文は保存時のキューに無いので、復元後に返金は再発生しない。
  - 費用: 復元は支払い処理を通らない。保存した国庫は支払済みの注文を既に差し引いた値で、`paid_cost` は注文側に保存される。国庫とキューは**同じファイル・同じ時点**で保存するので、片方だけが古い状態にならない(「取消し前の保存を読む」は国庫もキューも取消し前に戻るので二重返金ではない)。
  - 完成保留(Blocked): キューに残して復元し、翌日以降の完成処理が連続実行と同じ条件で再評価する。

### 5.2 `order_log` の扱い
- 役割は、二重処理の防止ではなく**拒否理由の区別**(`AlreadyCompleted` / `AlreadyCancelled` / `NoSuchOrder`)。ログが無くても返金は再発生しない(キューに無い注文は取消せない)。
- **推奨(現行ルールの保存)**: 全件を保存する(1件は識別子2つ+列挙値。注文数は小さい)。上限・切り詰めは**後で決められる**(§8 区分2)。切り詰めた場合、古い識別子の拒否理由が `NoSuchOrder` に変わる(返金には影響しない)。
- 復元時の整合性: ログの識別子は一意・`id.country` = 属する国家・`seq < next_order_seq`・キューに現存する識別子と重ならない。

### 5.3 静的データとの整合性(変化の種類ごとの推奨)
基準: **検証用形式(A)の既定は Strict**(保存時の署名と現在が違うものは、下表で「そのまま」「警告」とした種類以外は読込を拒否)。ゲーム用の既定を緩めるかは、ユーザー判断(§8 区分2)。**いずれの場合も、不整合を黙って補正せず、存在しないIDを別の土地へ割り当てない。**

| 変化 | 検出に使う情報 | 推奨 | 理由 |
|---|---|---|---|
| JSONの整形・配列順だけ | 地理の5種(順序非依存) | **そのまま復元できる** | 5種とも不変 |
| 地形・気候・植生・河川の属性変更(`attributes`/`rivers`のみ変化) | `GeographyChange` | **警告**(変更点を列挙して読込) | 経済の実行状態が現在これらを読まない。将来、属性に依存する規則(例: 地形で産出が変わる)を入れる場合は**拒否**へ引き上げる(規則の追加時に決める) |
| セル座標の**追加**(未割当のプロヴィンスとして) | ID集合・所属の署名 | **警告**(保存済みステートの所属が不変なら) | 保存データは `MapStateId` に結び付き、未割当の土地は含まれない |
| セル座標の**削除**(廃止ID)・保存済みステートの所属プロヴィンスの廃止 | ID集合・所属の署名、`retired` | **明示的な移行が必要(それまで拒否)** | ステートの構成が変わり、人口・施設の再配分は部分割譲のルール未決のため決められない |
| 陸↔水の変更 | `land_set` | 所属に影響しない(未割当)なら**警告**、保存済みステートの構成員なら**明示的な移行が必要(拒否)** | 水域は所属できない。構成員の水域化は所属の変更に等しい |
| プロヴィンスIDの変更・廃止 | ID集合の署名、`retired`・`next_province_id` | **拒否** | 別の土地へ割り当て直さない。ID再利用禁止の設計と整合 |
| ステート所属の変更(移動・分割・統合・新設・廃止) | 所属の署名・ステート集合 | **明示的な移行が必要(拒否)** | 人口・施設・注文の按分が未決(部分割譲・法的所有)。自動変換しない |
| シナリオの構造変更(国家の増減・ラベル・担当・`ai_controlled`・`military` 入力) | 構造署名 | **拒否** | 保存した国家・履歴・注文が意味を失う、または判断が変わる |
| 資源定義の変更 | `resources_signature` | **検証用: 拒否 / ゲーム用: 警告の余地**(区分2) | 鉱床は導出値なので復元自体は成立するが、産出・Mine注文の前提(未設定/設定済み)が変わり、再開一致が崩れる。既存のBlocked処理で扱える |
| 建物定義の変更(費用・必要進捗・労働・上限) | 建物定義の署名 | 費用・必要進捗の変更は**警告**(進行中の注文は保存済みの値を保つ)。**建物の削除**・保存済みの施設レベルが新しい上限を超える場合は**拒否**(上限超過だけは警告) | `paid_cost`・`required_progress` は注文が持つので進行中の注文は影響を受けない。未定義の建物は復元できない |
| 経済定数・計算式(コード)の変更 | `economy_rules_revision` | **拒否**(Strict)。ゲーム用の緩和は区分2 | 再開一致が保証できない。意図した調整なら、版の更新が移行の合図になる |
| 位置施設定義の変更 | (署名なし。現状は無関係) | **そのまま復元できる**(現状) | 経済状態へ影響しない。効果を実装する時点で署名を追加し、再分類する |

### 5.4 保存時の定義を同梱する方式と、現在のアセットを参照する方式
| | 同梱(スナップショット) | 参照(署名で束縛)【推奨】 |
|---|---|---|
| サイズ | 全域(陸34,503プロヴィンス)で大きい。資源・所属・施設定義を毎回複製 | 数個のハッシュだけ |
| 再開の確実性 | 保存時の定義で再現できる | アセットが変わっていれば検出して拒否/警告 |
| アセットの修正 | 既存セーブに**反映されない**(正本が2つ) | 反映される(ただし不一致は検出される) |
| 実装・保守 | 定義の読込経路が2系統になり、`WorldModel`・資源導出の再構築と二重化 | 既存の読込・導出経路をそのまま使う |
| リスク | 古い定義のまま走る・ID再利用との衝突を見落とす | 署名の取りこぼし(未署名の入力が変わる) |

推奨: **参照方式**。取りこぼしを防ぐため、§4.6 の入力ごとに署名を持ち、「署名の無い入力は経済状態へ影響しない」ことを設計の不変条件にする(位置施設が影響を持つ時点で署名を追加する)。注文が持つ `paid_cost`・`required_progress` は、定義が変わっても進行中の注文を守る目的で保存する。

## 6. 保存のタイミングと復元手順

### 6.1 安全な保存タイミング
- **`run_day` が戻った直後〜次の `run_day` の前**(日と日の間)。この間は、日次の建設・月次経済・AI履歴・AI評価が**すべて完了**している(月が変わった日も同じ。月次経済・履歴の記録・AI評価が `run_day` 内で終わっている)。
- この間に手動の `request_build`/`cancel_order` が行われてもよい(各呼び出しが原子的に完結する)。保存は注文の受付・取消しの「前でも後でも」整合する。
- **`run_day` の途中では保存しない**。途中の状態(建設は進んだが月次は未実行、など)を保存・復元する仕組みは作らない=不要な中間状態を永続化しない。ゲーム本体に組み込む際(Bevyの日次システム群)は、V1と同様に日次処理の連鎖の外側(日付更新・日次処理・履歴記録がすべて終わった後の段階)で保存する。
- 保存単位は `(日付, レジストリの動的状態, 全国家の動的状態)` を**1つのまとまり**(集約)として扱う。現在 `SimDate` が外にあるので、実装時に日付を含む集約(仮称 `MapEconomySimulation`)を導入する案を推奨(設計上の提案。コードは今回変更しない)。

### 6.2 復元手順(検証→再導出→一括置換)
1. ヘッダー(`kind`・`format_version`)だけを読む。不一致は本体を解析せず拒否。
2. 本体を解析する(失敗は拒否)。**ここまで現在の状態は一切変更しない**。
3. 現在の静的データ(地理/プロヴィンス表/所属/資源/建物/シナリオ構造)から**新規にステージ用の状態を構築**する(New と同じ構築関数。`MapStateEconomyRegistry::from_multi_scenario` → `attach_province_resources`)。
4. 静的データの署名を保存値と比較し、§5.3 の方針で 拒否/警告/許可 を判定する。
5. 保存DTOを検証する(日付・ID・参照先・範囲・キューと注文の不変条件・履歴の不変条件・識別子の不変条件)。問題は**すべて集めて**返す(最初の1件で止めない)。
6. ステージ用の状態へ、保存した動的値だけを上書きする(導出値 `resource_setup` は手順3の再導出)。
7. 全て成功したときだけ、`(日付, レジストリ, 国家)` を**1回の代入で**現在の状態と入れ替える。Rustでは、新しい値を完全に構築してから移動するので、**失敗したロードで国庫・キューなどが部分的に置き換わらない**。
- 復元は `place_order`・`run_day`・`cancel_order`・支払い・返金・完成処理を**呼ばない**。復元の結果が「その直前の状態」であり、副作用は無い。
- 警告は破棄せず、`LoadReport` として呼び出し側へ返す(CLIが表示する)。

## 9. 次段階の検証計画

### 9.1 新旧の比較と、新経路自身の保存前後の比較
- **新経路自身の保存前後の比較(今回のA)**: 保存→復元後の状態と、保存直前の状態が一致する。連続実行と、途中保存・復元後の実行が一致する。
- **新旧の比較**: 保存機構そのものは新旧で別形式なので、**新旧の一致は保存の検証対象にしない**(経済計算の新旧一致は P32-007〜012 で検証済み)。旧V1については「変更されない」「取り違えが拒否される」ことだけを検証する。

### 9.2 テスト(最低限)
1. **往復一致**: 復元した状態(日付・全ステート・全国家・キュー・識別子・AI状態・履歴)が保存直前と**ビット一致**(`f64`は `to_bits` 比較)。RONの文字列は2回の保存で同一(決定的な出力)。
2. **連続実行と再開の一致**: N日の連続実行と、k日→保存→復元→(N−k)日の実行で、最終状態と**復元後の日ごとの `DayReport`** が一致。kは以下を含む:
   - 月末(月が変わる日の前日/当日)
   - 建設完成の直前(完成日の前日、完成日当日の保存は「完成後」)
   - 履歴条件の成立直前(Iron継続不足の窓が揃う前の月、Factory飢餓の窓)
   - AIの初回評価の前(`dirty = true` の保存)
   - 完成保留(Blocked)の注文があるとき
3. **取消し後の二重返金なし**: 取消し→保存→復元→同じ識別子の取消しが拒否(`AlreadyCancelled`)され、国庫が変わらない。`order_log` を省いた変種でも返金は増えない。
4. **識別子の衝突なし**: 復元後に発行した識別子が、キュー・ログのどれとも一致せず `seq` が単調増加。国家ごとに独立。
5. **完成済みの再追加なし**: 完成直後に保存→復元→施設レベルが+1のまま(+2にならない)。完成済みの注文を意図的にキューへ残したDTOは `target_level` の不変条件で拒否。
6. **費用の再徴収なし**: 復元前後で国庫が一致(注文の `paid_cost` 分を再度引かない)。
7. **AI履歴の連続性**: 履歴の窓内の標本が復元後も同一。同じ日に同じ判断(`AiEvaluation`)が得られる。履歴を省いた変種は判断が変わる(=保存が必要であることの対照)。
8. **静的データ不整合の検出**: §5.3 の各行について、地理の再出力(整形のみ→許可、属性→警告、セル削除→拒否)、ID・所属・シナリオ構造・資源・建物・経済規則の変更を人工的に作り、期待どおりの 許可/警告/拒否 になる。存在しないIDを別の土地へ割り当てない。
9. **非対応形式・破損の拒否**: `kind` 不一致・`format_version` 不一致・未知のフィールド・欠落・RONの構文エラー・非有限の数値・負の人口に相当する値・範囲外・重複ID・存在しない `MapStateId`・不正な日付・履歴の順序違反/窓超過/未来の標本。
10. **失敗したロードで現在状態が変わらない**: 復元失敗の前後で、現在の `(日付, レジストリ, 国家)` が完全に同一(クローン比較)。
11. **旧V1セーブが変更されない**: `saves/savegame_v1.ron` のバイト列・更新日時が不変。新形式の保存先をV1のパスにすると書込拒否。V1のファイルを新形式の読込に渡すと `kind` 不一致で拒否、新形式のファイルをV1の読込へ渡すと拒否(既存動作の固定)。
12. **保存失敗時に既存ファイルを壊さない**: `rename` 失敗の注入で、既存の正常ファイルが内容も含めて保持され、`.tmp` が残らない(V1のテストと同じ手法)。
13. 不変条件の確認(実装時の調査として): 300日走行で、備蓄が負にならない/`living_standard`・`unrest` が範囲内/履歴が窓内、を確認し、復元時の検証範囲を実測で確定する(実測前に範囲を決めつけない)。
