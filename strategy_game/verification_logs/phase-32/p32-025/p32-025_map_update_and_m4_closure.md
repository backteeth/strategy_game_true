## 4. p32_005 の保証の整理

実コードと設計から確認した、旧確認「保存IDが全世界の初回採番と一致し、`next_province_id` が全陸セル数と一致する」が保証していたこと: ①保存IDが初回採番アルゴリズムと整合していること、②将来の本番表との衝突防止。ただし②は「保存IDが作成時の地図の初回採番」である間しか成り立たず、**陸セル集合が変わる地図更新後は、IDを振り直さない限り成り立たない**(振り直しは方針で禁止)。よって一致確認は不適切になった。失敗するアサーションを外したのではなく、次の2つの確認へ置き換えた。

- **A. 初回採番アルゴリズム**(`initial_numbering_is_deterministic_sequential_and_ordered`): 実地図の陸セル集合に対し、同じ入力から同じ表、IDは 0..n の連番、`(r,q)` 昇順で重複なし、陸セルのみ、件数 = 陸セル数、生成表が地理と整合。固定フィクスチャでの具体値と並び順非依存は既存の `p32_004` が引き続き確認。
- **B. 保存済みの区画定義**(`stored_ids_and_membership_are_kept_across_map_updates_and_reloads`): 29プロヴィンスの `(id,q,r)` と3ステートの所属を**固定値で明示**し、更新後の地図でそのまま存続すること、ID・セルの重複なし、陸のまま、`next_province_id` が最大IDより大きく 34503、表の対象外の陸にIDを発行していないこと、水域に区画がないことを確認。

併せて `p32_025_map_update_test.rs` に、地図の件数(96,760 / 陸35,221)、スキーマ拒否、検証地域の不変、m4d/m4e の組み立てと90日進行、新地図での保存→別セッション復元→継続(完全一致)、旧地図保存の判定(§5)を追加。他の過去テスト・記録は書き換えていない(今回の地図更新に伴う p32_001 のファイル名、p32_012 の湖数、p32_019 のダイジェスト定数の更新は、前回までに引き継いだ差分のまま)。

## 5. 旧地図で作った保存の判定

fixture: 更新前の地図・検証用ワールド(コミット済みの旧入力)から共有APIで作った保存(m4d、m4e。各45日進行後)を `tests/fixtures/p32_025/old_map_{m4d,m4e}.mapeco.ron` に固定(ユーザー保存は使っていない。試験は一時ディレクトリへコピーして実施)。

- `inspect`: 確認自体は成功し、**不適合(互換でない)**。拒否項目に `LandSet`(陸セル集合の変化)と `WaterKinds`(湖の数の変化)を含む。`ProvinceTable`・`StateMembership`・`ScenarioStructure`・`Grid`・`CellCoordinates` は一致。復元可能性の確認(`restorable`)には進まない。
- `load`: `FileError::Incompatible`で拒否。**現在の状態は変化しない**(`MapEconomySimulation` の完全一致で確認)。保存ファイルのバイト列も不変。
- つまり、IDと所属が維持されていても、陸水の変更は既存の判定表どおり拒否される。判定表・判定関数は変更していない。自動変換・移行機能・全不一致を無視する操作は実装していない。
- 新地図で作った保存: `inspect` は完全一致(exact)、`restorable` は成功、別セッションへ復元して完全一致、60日の継続も中断なしの実行と完全一致(m4d・m4e)。
