## 2. kind・形式バージョン・保存先
- 保存先: `<base>/map_economy/<名前>.mapeco.ron`(`<base>` は通常 `saves`。API/CLIで明示する)。名前は ASCII英数字・`_`・`-` の1〜64文字で、Windows予約名(CON/PRN/AUX/NUL/COM1-9/LPT1-9)は不可。
- 封筒: `(kind: "map_economy_state", format_version: 1, snapshot: (...))`。`snapshot` は P32-015 のDTO(`section_version`・`rules_revision`・`context` を含む)。
- 判定の順序: ヘッダー(`kind`/`format_version`/V1の`version`のみ)→ 別kind/旧V1/非対応版を識別して拒否 → 本体を厳密に解析(必須項目の欠落・未知のフィールド・型の不一致・途中切れを拒否)。非対応の版を現行版として推測しない。
- 欠落と明示的な空の区別: 空の履歴・空の注文一覧・空の `order_log` は `[]` として**明示されていれば受理**(日0のファイルで確認)。同じ欄の欠落、`ai`・標本の `units`/`unmet_milli` の欠落は拒否(serdeの既定「欠落した`Option`は`None`」を無効化)。

## 3. 保存先と旧V1の保護
- **パスの逸脱**: 名前に区切り・`.`・ドライブ・絶対パス・拡張子を含められない(`..`、`a/b`、`C:\x`、`\\server\share`、`x.mapeco.ron` 等を拒否。拒否時に何も作らない)。拡張子だけでは判断せず、保存先ディレクトリは `symlink_metadata` でリンクを拒否し、さらに `canonicalize` で実体が `<base>/map_economy` であることを確認する。既存のファイルがシンボリックリンクなら拒否。
- **旧V1**: 保存先は常に `.mapeco.ron`。`savegame_v1.ron` 相当(大文字小文字無視)・`.mapeco.ron` でないパスは `refuse_legacy_slot` で拒否。旧V1ファイルは、読み込み時に `NotThisKind(LegacyV1)`(`kind` が無く `version` を持つ形)として拒否し、**新形式として復元しない**。新形式のファイルは旧V1のDTOとして解析できないことも確認。
- **上書き**: 既存の保存先を置き換えるのは、**自形式として完全に解析できる場合だけ**。旧V1・別kind・非対応版・壊れた/途中切れ/空のファイル・ディレクトリは `OverwriteRefused`(または `LocationRefused`)で、内容はバイト単位で不変。
- 負例は一時ディレクトリ内の旧V1の**コピー**で実施。実ファイル `saves/savegame_v1.ron` は読み取りのみで、SHA-256 が作業前後で同一(`098b2175…`)、`src/save/`・`saves/` に差分なし。`saves/` に新しいファイルは作っていない。
- 利用者への明示: エラー文に「旧V1セーブ(別形式)であり、読み込みも上書きもしない」旨を表示する。

## 4. 原子的置換の実装とOS上の確認
手順: スナップショット取得 → 直列化 →(書いたものが同じスナップショットとして読めることを確認)→ 保存先の検証・既存ファイルの識別 → 同じディレクトリに一時ファイルを `create_new` で作成(`<ファイル名>.<pid>-<nanos>-<連番>.tmp`。自分が作ったものだけを扱う)→ `write_all` → `flush` → `sync_all` → ハンドルを閉じる → `std::fs::rename` で最終ファイルへ置換。**既存ファイルを先に削除する方法は使っていない。**
- 確認したOS: Windows 11(NTFS)。既存ファイルがある状態での `rename` による置換が成功し、置換後は新しい内容の完全なファイルになることをテストで確認(自形式への上書き保存)。
- 失敗の再現(`SaveIo`/`TempFile` を差し替える注入テスト): 作成・書き込み途中(半分だけ書いて失敗)・flush・sync・置換の各失敗で、(a) 既存の正常ファイルがバイト単位で同一、(b) 一時ファイルは自分が作ったものだけ削除、無関係なファイル(`keep.txt`・別の保存ファイル・古い`.tmp`風の名前)は不変、(c) 実行中のシミュレーションは不変、(d) エラーを返し成功と表示しない、(e) 失敗後も旧状態を完全に読める。初回保存の失敗では最終ファイルが作られない。置換失敗後に一時ファイルの削除も失敗した場合は、その旨をエラーに添え、残るのは自分の一時ファイルだけ。

## 5. 失敗時の保証範囲(確認していない保証は報告しない)
- 保証(テスト済み): この一連の操作の失敗では既存の保存ファイルが壊れない/書き込み途中の内容が最終ファイルに現れない/成功時は旧または新の完全なファイル。
- **保証していない・確認していない**: 電源断・OSクラッシュを含む永続性(ディレクトリエントリの同期は行っていない)。`rename` のクラッシュ時の原子性はOS/ファイルシステム依存で、確認していない。確認と置換の間に他のプロセスがファイルを書き換える競合(TOCTOU)も防いでいない(単一利用者のローカル保存を想定)。
- 環境の制約: **ファイルのシンボリックリンクの拒否テストは、この環境(権限なし)でリンクを作れず SKIPPED**(コードは `symlink_metadata` で拒否する実装だが、この環境では未実行)。ディレクトリのジャンクション(`mklink /J`)での保存先逸脱の拒否は実行して確認した。

## 6. コンテキスト照合の現状と未実装範囲
復元は 1. ファイル読み込み 2. 封筒の検証 3. DTO・コンテキストの検証 4. 候補状態の再構築 5. 成功時のみ置換、の順(P32-015の `restore`)。失敗した場合(`kind`不一致・破損・コンテキスト不一致・値の不正のいずれでも)現在の日付・国庫・人口・キュー・履歴は変わらない(クローンとの完全比較)。
- ファイル内の `context` は**採用せず**、復元先の静的入力から求めた値と照合する(`context` を書き換えたファイル、別シナリオの集約への復元はいずれも拒否。不一致を警告で通す例外は追加していない)。
- 現在、実際に照合している入力(内部のFNV-1a識別): 地理の5種の識別情報、各ステートの所属プロヴィンス、ステートの静的値(`workforce_ratio`・`base_logistics_capacity`)・鉱床、資源設定の状況、国家のラベル・AI国家か否か・担当ステート・軍事入力、建物定義の全項目。加えて `section_version` と `ECONOMY_RULES_REVISION`、ステート/国家の集合と順序。
- **まだ照合できていない/していない入力**: 位置施設の定義(現状は経済状態に影響しない)、翻訳等の表示データ、**コード上の経済式・定数の変更**(手で上げる `ECONOMY_RULES_REVISION` に依存)、地理JSONそのもの(プロヴィンス表に記録済みの識別情報との照合のみ)。外部署名による照合と判定表(属性変更は警告など)は P32-017。
- この識別はFNV-1a 64bitで、**暗号学的な真正性・改ざん防止の保証ではない**(同一コンテキストの取り違えを検出する内部の目印)。

## 7. 復元の二重処理防止(ファイル経由でも)
ファイル経由の復元で、国庫は保存値のまま(費用の再徴収なし)、完成済み施設は+1のまま(再追加なし)、取消し済み・完成済みの注文の取消しは `AlreadyCancelled`/`AlreadyCompleted` で拒否され国庫不変、復元後の新規注文IDは保存した `next_order_seq` から続く(テスト)。

## 8. CLIの使用方法と別プロセス再開
`world_economy_check` に明示的な操作を追加(引数なしの通常実行は従来どおりで、ファイルを作らない)。保存先は `--save-base` で必ず明示(既定の保存先は無い。省略するとエラー)。対象は m4d シナリオ(AI3国家・軍事入力・履歴・建設)で、初期注文や検証用操作の列は使わない(再適用するものが無い)。
```
cargo run -q --bin world_economy_check -- --economy-save <日数> --save-base <dir> --name <名前>      # 進めて、日と日の間で保存
cargo run -q --bin world_economy_check -- --economy-resume <日数> --save-base <dir> --name <名前>    # 別プロセス: 同じ静的入力を用意→復元→翌日から再開
cargo run -q --bin world_economy_check -- --economy-run <日数> [--digest-from <日数>]               # 連続実行(比較用、保存なし)
```
出力: 保存の成否・ファイル・日付、復元の成否・日付(最後に処理を完了した日。再開後の最初の処理日はその翌日)・失敗理由、各日の `day <日付> digest=<状態のFNV> treasuries=[...]`。
実行結果(`cli_save_resume_output.txt`): 100日進めて保存(14842バイト、1800/04/11)→ 別プロセスで復元して60日再開 → 連続実行160日の101〜160日と**60行すべて一致**(行数を確認して比較)。存在しないファイル・`--save-base` 省略は非ゼロ終了で失敗理由を表示。テスト(`a_separate_process_resumes_from_the_file_...`)は実際に3つのプロセスを起動して、保存日100日(途中)と30日(再開の最初の日が月次の日)で一致を確認し、旧V1のコピーを復元に渡すと「legacy V1」で失敗することも確認。
