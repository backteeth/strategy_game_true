# P20-008追補: 100州通常シナリオの性能回帰 — 原因分析と修正前後比較

## 1. 原因分析(実ソース確認)

### 1.1 キャッシュは実際に必要な日にだけ構築されていたか

`src/country/country_ai.rs::process_daily_country_ai` (修正前)は、`power_by_country` /
`land_states_by_controller` の2つの事前計算キャッシュを **日次評価の開始時に無条件で** 構築していた
(`ai_country_ids`ループに入る前)。

100州・国家8の合成ワールドでは、週次評価条件 `(current_day % 7 == country_id.0 % 7) || dirty` により、
国家ID 0〜7 に対して `day % 7` の値ごとに少なくとも1か国(`day%7==0`の日は国家0・7の2か国)が
毎日該当する。したがって「その日1件も対象国が無い」ケースはほぼ発生せず、
「必要な日にだけ構築する」という条件分岐だけでは、8か国規模のワールドでは
有意な削減効果は得られないと判断した(実測でも下記の通り、単純な条件分岐だけでは解決しなかった)。

### 1.2 固定費の正確な原因

回帰の実体は「キャッシュを毎日構築すること」自体ではなく、**`HashMap<CountryId, _>` という
データ構造そのものの定数項オーバーヘッド**(ハッシュ計算・バケット確保)であった。

`CountryId(pub usize)` は密な小さい整数キーであり、8〜100件程度の要素をHashMapに
`entry().or_insert()` で挿入する際のハッシュ計算コストは、削減できる走査コスト
(候補国7件に対する`O(states)`フィルタ再計算)と比べて、小規模では相対的に大きくなり、
回帰の一因になっていたと考えられる。

### 1.3 必要になる規模

500州(国家25)以上では明確に高速化する一方、100州(国家8)規模では
HashMap構築の固定費が支配的になる。詳細は下記の複数回計測比較を参照。

## 2. 採用した最小限の修正

1. **遅延構築**: `power_by_country` / `land_states_by_controller` を `Option<Vec<..>>` とし、
   その日最初に実際に必要になった国の処理時(`Option::get_or_insert_with`)にのみ構築する。
   全AI国家が交戦中で `process_war_preparation_ai` が1件も呼ばれない日には、
   構築自体を完全に省略できるようになった。
2. **HashMap → Vecインデックス化**: `CountryId(pub usize)` が密な整数キーであることを踏まえ、
   `HashMap<CountryId, u64>` を `Vec<u64>`(`country_id.0`で直接インデックス)に、
   `HashMap<CountryId, Vec<StateId>>` を `Vec<Vec<StateId>>` に置き換えた。
   ハッシュ計算を伴わないため、小規模でのオーバーヘッドが大幅に減少する。

**変更していないもの**: 判定ロジック・優先順位・戦力比較式・経路探索・週次/月次評価タイミング・
AIの意思決定結果・HashMap/Vecの走査順序(元の`state_registry.states`走査順=StateId昇順を
そのままVecへ反映)は一切変更していない。`test_compute_total_power_by_country_matches_individual_calculation`
/ `test_compute_land_states_by_controller_matches_individual_filter` で、新しい実装が
個別計算(`calculate_country_total_power`、直接フィルタ)と完全に一致することを検証済み。

## 3. 修正前後の複数回計測比較(100州・通常シナリオ)

同一マシン・releaseビルド・固定Seed(`0x00C0FFEE12345678`)で、修正前(HashMapベース)・
修正後(Vecインデックス+遅延構築)それぞれ独立に5回ずつ計測した。生ログは
`pre_fix_runs/run1.log`〜`run5.log`、`post_fix_runs/run1.log`〜`run5.log`を参照。

### 3.1 生データ(各実行のmean/median、単位ms)

| 実行 | 修正前 mean | 修正前 median | 修正後 mean | 修正後 median |
|---|---|---|---|---|
| run1 | 0.3036 | 0.3003 | 0.0775 | 0.0708 |
| run2 | 0.1385 | 0.1237 | 0.0846 | 0.0761 |
| run3 | 0.1418 | 0.1377 | 0.0941 | 0.0810 |
| run4 | 0.0733 | 0.0694 | 0.0916 | 0.0781 |
| run5 | 0.0809 | 0.0785 | 0.0955 | 0.0792 |

### 3.2 集約統計

| 指標 | 修正前 | 修正後 | 変化 |
|---|---|---|---|
| mean-of-means | 0.1476ms | 0.0887ms | **-39.9%** |
| median-of-medians | 0.1237ms | 0.0781ms | **-36.9%** |
| 標準偏差(mean間) | 0.0830ms | 0.0067ms | **-91.9%** (分散が大幅縮小) |
| 変動係数(CV = 標準偏差/平均) | 56.2% | 7.6% | 実行間のばらつきが大幅に安定化 |
| 最小mean | 0.0733ms | 0.0775ms | ほぼ同水準 |
| 最大mean | 0.3036ms | 0.0955ms | 最悪ケースが大幅改善 |

### 3.3 結論

- 単発計測(当初報告の0.0813ms→0.1152ms、41.7%悪化)は、修正前HashMap実装の
  試行間ばらつき(0.0733ms〜0.3036ms、変動係数56%)の範囲内に収まる**測定ノイズが主要因**であった。
  当初の「後」の値(0.1152ms)はこの分布の中央付近、「前」の値(0.0813ms)はこの分布の
  低い側の値であり、単発比較では回帰と誤認しうる差でしかなかった。
- 修正後(Vecインデックス+遅延構築)は、平均・中央値の両方で修正前の平均的性能を上回り
  (mean-of-means -39.9%、median-of-medians -36.9%)、かつ試行間のばらつきも
  劇的に縮小した(標準偏差 -91.9%、変動係数 56.2%→7.6%)。
- したがって、100州通常シナリオの性能回帰は**解消**しており、かつ副次的に
  小規模での実行時間の予測可能性(分散)も大幅に改善したと判断する。

## 4. 500〜2000州の改善維持確認

`smallscale_fix_final`(決定版フル計測、`../smallscale_fix_final/`参照)および
上記5回バッチの500/1000/2000州データにおいても、修正前ベースライン
(`../baseline/`、2000州normal median=5.057ms)と比較して大幅な改善を維持していることを確認した
(2000州normal median: 決定版0.192ms、5回バッチ平均的には0.42〜0.52ms、
いずれも修正前ベースラインを大きく下回る)。詳細は報告書本体の表を参照。
